# Operations guide

This document covers the prerequisites and recovery procedures for the archive and publication workflow. The public explanations are generated by AI from primary sources. They are an independent civic aid, **not legal advice**, and must not be used as a substitute for the Court's documents or advice from a qualified lawyer.

## Local prerequisites

Use a Linux or macOS checkout with:

- Git (ordinary Git is used for PDFs; Git LFS is not used)
- the Python version declared by `pyproject.toml`, with `venv` and `pip`
- Node.js and npm versions compatible with `site/package.json` and `site/package-lock.json`
- enough disk space for the checkout, the immutable PDF archive, Python/Node dependencies, and temporary extraction data
- network access to the configured Supreme Court sources; generation also requires access to Ollama

Create an isolated development environment and install locked site dependencies:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -e .
npm --prefix site ci
```

Do not run the pipeline or npm with `sudo`. The checkout and generated files should belong to the developer or runner service account.

## Repository data boundaries

| Path | Owner/purpose | Mutation rule |
| --- | --- | --- |
| `documents/` | ingestion; content-addressed source PDFs | append immutable blobs; never rewrite accepted bytes |
| `manifests/` | ingestion; retrieval and provenance records | reconcile atomically; retain superseded records |
| `data/cases/` | ingestion/normalization; factual case records | update only from supported metadata |
| `data/evidence/` | extraction; page-aware evidence | generated and reproducible from archived sources |
| `data/guides/` | verification; accepted public guides | replace only after all acceptance checks pass |
| `data/checkpoints/` | orchestrator; durable backfill progress | commit after bounded work |
| `reports/` | all stages; diagnostics and run outcomes | safe to retain; never treat a report as accepted content |
| `site/` | SvelteKit presentation source | must consume accepted data and must not copy PDF bytes |

On `spark`, the runner service user must own the Actions work directory and any tool caches it uses. A typical one-time check is:

```bash
sudo chown -R <runner-user>:<runner-group> /path/to/actions-runner /path/to/actions-work
sudo -u <runner-user> test -w /path/to/actions-work
```

Use the actual installation paths and account. Do not make the checkout world-writable. Ollama may run as a different service account; it only needs network access from the runner, not write access to this repository.

## Ollama

The production defaults are:

```text
OLLAMA_BASE_URL=http://192.168.1.41:11434
OLLAMA_MODEL=ragchew-gpt-oss:120b-32k
OLLAMA_CONTEXT_LENGTH=32768
```

Set repository variables `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, and optionally `PAGES_ARTIFACT_MAX_MIB` to override workflow defaults. Keep private credentials in GitHub Actions secrets, never in repository variables or committed `.env` files. The current LAN Ollama endpoint does not require a credential.

Before generation, verify connectivity and model availability from the runner account:

```bash
curl --fail --show-error --silent "$OLLAMA_BASE_URL/api/tags"
curl --fail --show-error --silent "$OLLAMA_BASE_URL/api/show" \
  -H 'Content-Type: application/json' \
  -d "{\"name\":\"$OLLAMA_MODEL\"}"
```

The model must be configured for a 32,768-token context. The pipeline still chunks below that ceiling; increasing a request beyond the configured context is not a substitute for chunking. Record the model digest with each accepted guide.

## Common commands

Inspect the installed command before an operation:

```bash
scotus-guide --help
scotus-guide ingest --help
scotus-guide extract --help
scotus-guide generate --help
scotus-guide recover --help
```

The workflow uses the following stable command contract:

```bash
# Discover current sources, extract evidence, then generate affected guides.
scotus-guide ingest --mode incremental --batch-size 25
scotus-guide extract --mode incremental --batch-size 25
scotus-guide generate --mode incremental --batch-size 25

# Process one bounded historical batch. Its checkpoint is checked in.
scotus-guide ingest --mode bounded-backfill --batch-size 10
scotus-guide extract --mode bounded-backfill --batch-size 10
scotus-guide generate --mode bounded-backfill --batch-size 10

# Regenerate one case from already archived inputs.
scotus-guide extract --mode case-regeneration --batch-size 1 --case-id <stable-case-id>
scotus-guide generate --mode case-regeneration --batch-size 1 --case-id <stable-case-id>

# Deterministically inspect historical PDFs without changing canonical metadata.
# These defaults write reports/recovery/plan.json and reports/recovery/report.json.
scotus-guide recover --plan

# Apply that exact reviewed plan atomically (no extraction or model calls).
scotus-guide recover --apply

# Deterministic schema, citation, lifecycle, and archive checks only.
scotus-guide validate

# Site checks and static output.
npm --prefix site run check
npm --prefix site test
npm --prefix site run build
scripts/check-pages-artifact.sh site/build 100
```

In normal production operation, dispatch **Update archive and publish citizen guide** in GitHub Actions instead of manually committing output. Choose `incremental`, `bounded-backfill`, `case-regeneration`, `guide-regeneration`, `validation-only`, `historical-recovery-plan`, or `historical-recovery-apply`. A case ID is mandatory for either regeneration mode. `case-regeneration` re-extracts evidence before rebuilding the guide; `guide-regeneration` reuses the currently accepted evidence and is appropriate after a synthesis-only fix. The two recovery operations are described below. Batch size is limited to 1–100 and is ignored by recovery. The nightly schedule runs incremental mode at 08:17 UTC.

## ARM64 `spark` runner

The self-hosted runner must:

1. Be registered to a trusted repository or organization and show both `self-hosted` and `spark` labels.
2. Run on ARM64 Linux (`uname -m` should report `aarch64`).
3. Run as an unprivileged, dedicated service account with write access to its Actions work directory.
4. Have `git`, `python3`, and `curl` on `PATH` for that service account. The workflow installs its locked Node.js runtime with `actions/setup-node`.
5. Reach GitHub Actions, official source hosts, and `OLLAMA_BASE_URL` over the LAN.
6. Have sufficient persistent disk for a full Git checkout. Monitor both free disk and repository growth.

Keep the runner application current and run it as a supervised service. Do not add `pull_request` or `pull_request_target` triggers to a job using `spark`: public pull-request code must never execute on the LAN-connected runner.

Repository settings must allow GitHub Actions, permit the workflow's scoped `GITHUB_TOKEN` to write repository content, and configure Pages to use **GitHub Actions** as its source. Preserve the `scotusbriefs.us` custom domain and DNS settings. The workflow itself grants no default permissions: the pipeline gets `contents: write`; only the deploy job gets `pages: write` and `id-token: write`.

## Launch status and source coverage

The public catalog launched on 2026-09-18 at `https://scotusbriefs.us/`. The initial
repository contains 2,161 immutable PDFs, 1,797 case/group records, 10 normalized curated
cases, and four accepted citizen guides spanning a pending case, a consolidated case, an
application docket, and an ordinary merits case. The nightly schedule is active at 08:17 UTC.

Known launch limitations:

- 1,787 historical export groups retain opaque identifiers until authoritative docket metadata
  can be recovered; they remain archived but are intentionally excluded from public browsing.
- Guide coverage is intentionally sparse while the resumable backfill runs. Missing sections
  remain pending or source-limited rather than being filled from model memory.
- OCR requires an explicitly configured `SCOTUS_OCR_COMMAND`; without it, pages lacking usable
  embedded text are marked unavailable and cannot support claims.
- Current discovery depends on the documented Supreme Court source pages and may require adapter
  updates if the Court changes its markup or URLs.

Continue historical processing with a small monitored batch, then increase only after reviewing
validation reports and repository growth:

```bash
# Preferred: dispatch this mode in the publication workflow.
scotus-guide extract --mode bounded-backfill --batch-size 5
scotus-guide generate --mode bounded-backfill --batch-size 5
```

The first checked-in backfill checkpoint completed `2024-24-249`; rerunning bounded backfill
resumes after accepted cases. Recovery procedures are below.

## Historical metadata recovery

Recovery is deterministic and uses only preserved import paths and archived PDF text. It does not
use Ollama. Prefer the serialized workflow operations so the reviewed transaction and applied
source state have durable commit boundaries:

1. Dispatch `historical-recovery-plan`. It writes and commits
   `reports/recovery/plan.json` (the transaction and source hashes) and
   `reports/recovery/report.json` (coverage and conflicts). It does not change `manifests/` or
   `data/cases/`, run repository/site validation, build, deploy, extract evidence, or contact
   Ollama.
2. Review the committed plan and report. For every proposed component, confirm the docket set,
   title/caption, term, lifecycle and dates against the listed PDF hashes and field provenance.
   Review every split group, merged group, existing-case mapping, warning, and conflict. Confirm
   unresolved or ambiguous documents are not assigned, curated metadata is not weakened, and no
   unexpected case ID or primary-docket collision is proposed. Do not apply while unexplained
   conflicts or implausible coverage changes remain; fix the deterministic parser and make a new
   plan instead of hand-editing the JSON transaction.
3. Dispatch `historical-recovery-apply` only while the reviewed plan is still the canonical file
   on the default branch. Apply verifies the recorded manifest and case hashes, archived bytes,
   and complete transaction before atomically changing the manifest and case records. A stale or
   malformed plan fails before canonical writes.
4. The workflow commits the applied manifest, case metadata, and durable recovery report as
   source state. Only after that commit succeeds does it run repository validation, site checks,
   tests, build, artifact guards, and deployment. Apply does not generate guides or contact
   Ollama.
5. Inspect `reports/recovery/report.json` and the workflow summary. `cases_written`,
   `unresolved_cases_removed`, `unresolved_cases_reduced`, and `manifest_changed` must match the
   review. To prove idempotence, create and review a fresh plan against the new source hashes and
   apply it; the report should show `no_op: true` and no canonical changes.

Local commands accept `--root`, `--manifest`, `--plan-path`, and `--report` for fixture or recovery
worktrees, but production uses the canonical defaults above. Plan generation leaves manifest and
case files byte-for-byte unchanged. Do not combine plan and apply into an unreviewed command.

Recovery makes docketed cases eligible for the existing resumable pipeline; it intentionally does
not start an unbounded generation run. After a successful apply, dispatch a small, monitored
`bounded-backfill` (start with `batch_size: 5`). Review extraction/generation reports and repository
growth after each committed batch, then continue from the checked-in checkpoint. Ambiguous
unresolved groups remain excluded. Never increase the bound merely to bypass a failing case.

### Rolling back historical recovery

Stop new publication runs and identify the source-state commit produced by
`historical-recovery-apply`. If bounded backfill commits were made afterward, revert those commits
first in reverse order so guides, evidence, and checkpoints cannot refer to cases being restored.
Then use `git revert <recovery-commit>` on the current default branch. The revert should restore
both `manifests/documents.json` and affected `data/cases/*.json` plus the recovery report; it must
not delete or rewrite anything under `documents/`. Run `scotus-guide validate` and dispatch
`validation-only` to rebuild and deploy the restored checked-in state. Never force-push, reset the
default branch, delete immutable PDFs, or edit a recovery plan to simulate rollback.

## Publication behavior

`.github/workflows/publish.yml` serializes all publication runs and never cancels an active run. It does not run on pull requests.

For incremental and backfill operations it performs these durability boundaries:

1. ingest and validate source documents;
2. commit and push only `documents/`, manifests, factual case/checkpoint state, and reports;
3. extract, generate, and verify guides;
4. commit and push only accepted evidence/guides, checkpoints, and reports;
5. validate all repository data;
6. check, test, and build the SvelteKit site;
7. reject a Pages output containing a `.pdf`, PDF signature, symbolic link, or more than the configured size limit;
8. upload and deploy through GitHub Pages.

The commit helper avoids empty commits and stages only phase-owned paths. It verifies that the remote branch has not moved, then pushes without rebasing or force-pushing, so the pushed tree is exactly the validated tree. A concurrent update fails closed and leaves a recoverable Git bundle in the run reports. Workflow logs alone are excluded from commits, so a no-change nightly run does not create a content commit. A final current-revision guard prevents a stale build from being uploaded. Thus an Ollama, validation, build, or deployment failure cannot discard an already archived source. A failed build is never uploaded, and a failed deployment does not delete the last successful Pages site.

Each run writes a GitHub step summary and retains `reports/` as an Actions artifact for 30 days. CLI reports should provide per-item discovery, archive/import, extraction, generation, and validation detail; the workflow adds build and deployment outcomes.

## AI and legal-information policy

Generated text must:

- be clearly identified as AI-generated, independent plain-language explanation;
- cite the primary documents and page ranges supporting material claims;
- distinguish allegations, party and amicus arguments, oral-argument questions, holdings, concurrences, and dissents;
- never infer a vote or holding from a justice's question;
- show pending or source-limited states rather than fill gaps with model knowledge;
- avoid predicting undecided cases;
- preserve qualifications and uncertainty; and
- state prominently that the guide is not legal advice.

Only schema-valid, citation-valid, lifecycle-consistent, verified guides are publishable. Rejection must leave the prior accepted guide unchanged. Readers should always be directed to official and archived primary sources.

## Failure and recovery

Start with the failed run's step summary and its `operation-reports-<run>-<attempt>` artifact. Never delete archived PDFs or reset the default branch to hide a failed operation.

### Ollama, extraction, or guide validation fails

The source-preservation commit should already be on the default branch. Confirm it in the run summary and Git history. Restore Ollama or correct the extraction/validation issue, then dispatch `case-regeneration` for an extraction change, `guide-regeneration` for a synthesis-only change, or rerun the bounded operation. The last accepted guide and public site remain in place.

### Source commit or push fails

The runner checkout may still contain validated files. Stop other publication work, preserve that worktree, and inspect `git status` and the run log. Fetch the default branch, resolve without dropping `documents/` blobs or manifests, and run the commit helper intentionally:

```bash
ALLOW_LOCAL_WORKFLOW_COMMIT=1 scripts/commit-workflow-state.sh source \
  'chore(archive): recover preserved workflow sources'
```

The helper pushes only when its parent is still the current remote revision; it never rebases or force-pushes validated output. On a push race, download `reports/workflow/unpushed-source.bundle` from the run artifact, fetch it into a clean current checkout, reconcile while retaining both immutable blobs, rerun validation, and push the recovered commit normally.

### Build or artifact check fails

No Pages deployment is attempted. Fix the data or site issue and dispatch `validation-only`; it validates and rebuilds the checked-in state without contacting Ollama or changing guides. If the size guard failed, inspect `site/build` for accidentally copied archives or unexpected assets. Do not simply raise the limit until the growth is understood.

### Pages deployment fails

The prior Pages deployment remains served. Use GitHub's **Re-run failed jobs** after a transient Pages incident. For a bad but successfully deployed revision, revert the responsible data/site commit on the default branch (do not remove immutable source PDFs), then dispatch `validation-only` to build and deploy the restored state.

### Backfill is interrupted

Use the last committed file under `data/checkpoints/` as the durable boundary. Rerun `bounded-backfill` with a suitable batch size. Do not hand-edit a checkpoint merely to skip a failure; retain the report, correct the case or source issue, and resume.

### Runner is offline or disk is full

No new deployment occurs. Bring the supervised runner service back online, or free only reproducible caches (`.venv`, `site/node_modules`, SvelteKit build/cache directories). Do not delete `documents/`, manifests, accepted guides, or checkpoints from an unpushed worktree. Verify Ollama connectivity and disk headroom before rerunning.
